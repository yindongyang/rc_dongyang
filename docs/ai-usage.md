# AI 使用说明

> 这份文档**比代码本身更能体现作业意图**。它说明：哪些地方让 AI 帮上了忙、哪些 AI 建议被我**主动拒绝**、哪些关键决策是我自己做的。

使用模型：Claude（主力做架构与代码生成）。下文所有"AI 建议"指对话中真实出现过的方案讨论。

## 2. AI 建议过、但**我没有采纳**的内容

这部分体现"对 AI 输出的判断、修正与取舍"。

### 2.1 引入 Kafka / RocketMQ 做"削峰解耦"
- **AI 理由**：消息中间件是异步通知系统的"标准件"，做削峰、解耦、回放
- **我的拒绝**：MVP 阶段流量未知（很可能 < 100 QPS），DB 当队列完全够用。引 MQ 反而引入"DB 状态与 MQ 消息双写一致性"的新难题。**等到流量证明了瓶颈，再演进到 v3**（README §6 写明）

### 2.2 引入 Redis 做幂等去重
- **AI 理由**：Redis SETNX 性能高、TTL 自动过期
- **我的拒绝**：业务幂等 key 是低频写入场景，DB `UNIQUE (biz_system, biz_id)` 一行索引就够。多一个组件多一份运维与故障源

### 2.3 用 SAGA / 事务消息做最终一致
- **AI 理由**：跨服务一致性的常见方案
- **我的拒绝**：本服务**业务方不关心外部返回值**，根本没有"跨资源一致性"的语义需求。SAGA 在这里是无的放矢

### 2.4 给每个供应商写一个 adapter
- **AI 理由**：扩展性好，方便将来接新供应商
- **我的拒绝**：**协议统一是 HTTP**，差异在 URL/Header/Body，配置化即可。adapter 模式只在"协议异构"（如混合 HTTP + gRPC + AMQP）时才值得。这是典型的"过度面向未来设计"

### 2.5 用 Hystrix / Sentinel 做完整熔断器
- **AI 理由**：成熟方案，支持降级、舱壁、限流
- **我的拒绝**：MVP 用一个 vendor 维度内存级"连续失败 N 次挂起 M 分钟"的简单短路就够。把熔断器当"零成本默认引入" 是新人易犯的错——它带来配置复杂度、误判风险、与重试策略的耦合

### 2.6 全套 OpenTelemetry 链路追踪
- **AI 理由**：现代云原生应用的标配
- **我的拒绝**：MVP 只需结构化日志 + traceId 透传 + 几个内存计数器。Otel 集成要 collector / backend / 配置，对一个本地能跑的演示项目就是负担。在 README §6 演进到 v4 再补

### 2.7 自研一致性 hash 分配 vendor → worker
- **AI 理由**：避免单 vendor 拖垮整体
- **我的拒绝**：**单进程协程池 + DB 抢占** 在 v1 阶段够用；演进到 v3 引 Kafka 后用 partition 天然解决，没必要在 v1 自研

### 2.8 用 gin + viper + zap + cobra 全家桶
- **AI 理由**：生态成熟，开发更快
- **我的拒绝**：路由 5 个、配置 1 个、日志用 `log/slog`（Go 1.21+ 标准库）。引一堆依赖反而把"我看了就懂"的门槛抬高，对评审不利

### 2.9 任务表加 vendor / 优先级 / 租户 等字段
- **AI 理由**：方便未来扩展
- **我的拒绝**：YAGNI。需求里没有，加了就要测、要文档、要回收。等真的有这些诉求时再加列

## 3. **我自己做出的关键决策**及理由

### 3.1 选择 SQLite 作为 MVP 默认存储（而非 MySQL/Postgres）
**理由**：评审能 `go run` 一键复现，不需要 docker-compose。`Store` 接口抽象后切 MySQL 只是改 DSN。**让评审者 30 秒内跑起来**比"贴近生产"更重要。

### 3.2 API 与 Worker 同进程（goroutine 池），但保留拆分能力
**理由**：MVP 同进程减少运维负担；Worker 抢占基于 DB 而非内存队列，所以将来拆成两个二进制（`cmd/server` + `cmd/worker`）几乎零成本。**这是"未来不付代价"的扩展性**，不同于"现在就为未来付代价"的过度设计。

### 3.3 重试责任不下沉到外部（不让外部供应商配合做去重逻辑）
**理由**：我们能控制的只有自己。在 Header 里透传 `Idempotency-Key` 是"建议"而非"依赖"。即使供应商没实现去重，业务方也能基于 `biz_id` 自己处理。**永远不要把可靠性建立在你不能控制的环节上**。

### 3.4 4xx 不重试（除 408/429）
**理由**：4xx 表示请求本身有问题，重试无意义只会浪费容量、放大错误。直接进死信、人工介入。这是真实工程经验——**新手最爱"无脑全重试"，结果把外部 API 打挂还是失败**。

### 3.5 Worker 抢占用乐观锁而非 `SELECT FOR UPDATE`
**理由**：SQLite 不支持 `SKIP LOCKED`；`FOR UPDATE` 在多 worker 下会串行化吞吐。乐观锁 `UPDATE WHERE status='pending'` 行为简单，多 worker 下天然分散冲突。切到 MySQL 后可升级为 `SKIP LOCKED`。

### 3.6 没做权限/鉴权
**理由**：MVP，定位"内部服务，假设上游可信"。在 README §2.2 明确写出来。**做减法且明示，比偷偷不做更专业**。

### 3.7 文档比代码长
**理由**：作业明确说"我们更关注的是你如何在 AI 的辅助下做工程决策，而不是完成这个需求"。**README + 这份 AI 使用说明就是答卷主体**，代码只是论据。

## 4. 我对 AI 输出的整体观感

- AI 善于**广度**（"还可以加 X、Y、Z"），但**收敛能力差**——总倾向加东西，少建议砍东西
- AI 给出的"行业标准做法"很多时候是**生产级**默认，对 MVP 是过度
- AI 不会主动质疑需求边界（比如不会问"业务方真的不关心返回值吗？"），需要工程师主动复读需求并坚持
- AI 在**细节正确性**上很有价值（408/429、jitter、`Retry-After`、`SKIP LOCKED` 这类"老司机才记得的点"）
- 最大风险：**让 AI 一把梭出一个看似完整的方案，会显得"什么都做了"，但每一项都很浅**。本次我刻意做减法，把"明确不做"列得比"做了"还细。
